# ADR 0002 — Auth, контакт и переписка

**Обновлено**: 03.11.2026

## Статус

Принято.

## Контекст

Приложение **только для Беларуси**. Нужны несколько способов входа, безопасный контакт и сделки **внутри** продукта — без увода диалога в мессенджеры/почту.

Открытый выбор по email: пароль vs magic link (сравнение и решение ниже).

## Решение

### Auth (MVP)

| Канал | Поведение |
| --- | --- |
| Email | **пароль** + сброс через письмо со ссылкой |
| Телефон | OTP (SMS, провайдер BY — отдельно) |
| Google | OAuth |
| Telegram | Login Widget / Bot-based login |

Библиотека: **Better Auth**. Сессия cookie; проверки на сервере.

**Где живёт auth:** в том же Next.js-приложении (не отдельный auth-микросервис/контейнер в MVP). Вынос оправдан позже при втором клиенте (mobile) или отдельной команде identity — до этого лишние сеть, деплой и CORS/cookie-домены. Граница чистая: use-cases зависят от порта сессии, не от UI.

Один `User` — несколько `Account`. Верифицированный `phone` в профиле — для показа контакта авторизованным.

#### Email: пароль vs magic link

| | Пароль | Magic link |
| --- | --- | --- |
| Плюсы | Быстрый повторный вход; не зависит от доставки письма каждый раз; привычно для досок объявлений | Нет пароля → меньше утечек/забывания; проще первый вход с нового устройства |
| Минусы | Нужны хранение hash, сброс пароля, риск stuffing; пользователь забывает пароль | Каждое «войти» = почта (спам/задержка mail.ru/yandex); плохой UX с телефона, если почта на ПК; слабее для частых заходов в inbox |

**Выбор: email + пароль** (сброс — одноразовая ссылка в письме).

Почему: уже есть passwordless-каналы (Google, Telegram, phone OTP). Для email нужен стабильный «классический» вход — пользователи будут часто заходить в **внутреннюю переписку**. Magic link как единственный email-способ даёт лишнее трение и зависимость от почты. Отдельный passwordless-email в MVP не делаем (YAGNI).

### Контакт и переписка

1. Кнопка **«Написать»** на карточке → тред в приложении (`Message` / `Conversation`).
2. Переписка **только внутри приложения**. Не отправляем текст сделки в email/Telegram/SMS и не подталкиваем «напишите в TG».
3. Уведомления снаружи (если появятся позже) — только «есть новое сообщение, откройте приложение», без тела переписки и без альтернативного канала сделки. В MVP notify можно отложить.
4. **Телефон автора** — только авторизованным; гостю CTA входа.
5. Писать и смотреть телефон — только authenticated.

Цель: интерес и договорённости остаются в продукте.

### Регион

Только РБ: справочник городов, BYN, маска `+375`.

## Последствия

- Нужны: Google OAuth, Telegram bot, SMS gateway, SMTP (сброс пароля).
- Inbox/threads в домене и UI; realtime не обязателен в MVP (poll / refresh).
- Телефон и сообщения не отдавать гостям.
- Rate limit: OTP, login, create listing, send message.
